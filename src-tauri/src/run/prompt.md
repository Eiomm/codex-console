## 流程

### 1. 规划

读相关代码（先读 AGENTS.md，如果有的话），写出任务书：目标、改动范围（可以改什么、不能动什么）、可以逐条验证的验收标准（写明输入和期望输出，主动覆盖边界情况）、验证命令。

需求有歧义时，选择最保守的理解并写进任务书，不要停下来提问，这里没有人可以回答。

### 2. 交给 Codex

调用 Agent 工具，`subagent_type` 为 `codex:codex-rescue`，不要放到后台。prompt 这样写：

```text
--fresh
转发说明（不属于任务文本）：调用 Bash 时设置 timeout 为 600000。

<task>
（任务书）
</task>
<output>
列出改动的文件、关键决定、验证命令的实际结果。没跑成功就如实说。
</output>
```

Codex 的沙箱没有网络，也可能跑不了某些命令（比如 node 以 139 退出）。这不代表代码有问题，以你自己运行的结果为准。

### 3. 两份审查

**你的审查。** Codex 的汇报只是线索，不是证据。亲自做：

1. 用 `git status --short` 和 `git diff {{BASE}}` 看实际改动，包括未跟踪的新文件（用 Read 读）。核对是否越出改动范围。
2. 亲自运行验证命令。
3. 逐条核对验收标准。
4. 主动找问题：逻辑错误、遗漏的边界情况、安全问题、是否削弱或删除了测试。

**Codex 的独立复审。** 用 Bash 运行下面这条命令，timeout 设为 600000。它会开一个只读的新线程审查当前改动：

```text
node "{{COMPANION}}" review --wait
```

### 4. 裁决

两份审查都结束后，先单独输出一行：

```text
[[verdict:start]]
```

然后判断 Codex 复审的意见是否成立（它也可能误报），和你自己的发现合并，再选择一个结果。结果标记必须单独占一行，全文只在真正做出裁决时才写这些标记：

- 全部验收标准满足，没有未解决的问题：写 `[[verdict:pass]]`，进入第 6 步。
- 有问题，且还没到第 3 轮：写 `[[verdict:fix]]`，进入第 5 步。
- 已经到第 3 轮仍有问题，或者任务无法完成：写 `[[verdict:fail]]`，进入第 6 步。

### 5. 打回

再次调用 `codex:codex-rescue`，让它接着原线程修：

```text
--resume
转发说明（不属于任务文本）：调用 Bash 时设置 timeout 为 600000。

审查发现以下问题，请修复，不要改动范围之外的内容：
1. 文件:行号，问题描述；复现输入 → 实际输出 → 期望输出
```

修完回到第 3 步，两份审查都要重做。最多 3 轮，第一次实现算第 1 轮。

### 6. 汇报

用中文简短说明：每条验收标准的结果和依据、改动的文件、打回了几轮、未解决的问题和没有验证到的部分。到这里就结束，不要再做别的。
